# 手写笔电量与充电状态：实机记录与一处前提的更正（2026-11-28）

作者：SZTM　设备：HUAWEI MateBook E Go（gaokun3，crDroid 13 / Android 17），M-Pencil（内核节点只报 `M-Pencil`，读不到 CD54/CD54R 与固件版本）。

这份记录做两件事：撤回我们此前提出的一个前提，并给出在干净条件下重测的观测。本记录不包含代码改动。

## 1. 被撤回的前提

我们在 PR #222 与 issue #223 里写过：

> The MCU does not send the level (0x08) or the charging state (0x09) on its own: PC Manager's PenService.dll asks for them with 0x0801 (CommandSendGetPenBattery) and 0x0901…

这个前提不成立。两个部分分别错在不同的地方。

### 1.1 “PenService.dll 会查电量”这一说法的来源

我们是从 OpenEGo Hub 项目（NihilDigit/openego-hub）的 Windows 侧实现里读到它的，原文如下（行号依据该仓库 `main` 分支 commit `21d6875`，2026-11-16）：

| 位置 | 内容 |
|---|---|
| `hal/src/pen/PenService.cpp:279` | `m_module = LoadLibraryW(L"PenService.dll");` |
| `hal/src/pen/PenService.cpp:288` | `ResolveOptional(dll, "CommandSendGetPenBattery", g_api.getBattery);`（相邻还有 `CommandSendGetPenChargingStatus` 等） |
| `hal/src/pen/PenHostMain.cpp:22-32` | 注释“PenService.dll 随 PC Manager 的配件中心安装”，并在 `C:\Program Files\Huawei\PCManager\components\accessories_center\accessories_app\AccessoryApp\Lib\Plugins\Depend\PenService.dll` 探测 |
| `EGoTouchService/Device/btmcu/PenUsbTypes.h:60` | `QueryPenBattery = 0x0801,       // PenService: CommandSendGetPenBattery` |
| `EGoTouchService/Device/tests/btmcu/PenUsbProtocolPacketTest.cpp:179-187` | 注明 `0x0801` / `0x0901` 的字节“唯一的校验来源”是“原厂 PenService.dll 里的栈上立即数” |

需要说明的是：该仓库自己也写明“不同版本的 PenService 导出并不完全一致”“随 HuaweiPenApp 分发的那份据报没有这个导出”，它并没有担保 PC Manager 14.0.7.310 里存在这个 DLL。错在我们把这份 Windows 实现当成了 PC Manager 的事实，没有独立核实就写进了补丁注释、PR 与 issue。

维护者解包 PC Manager 14.0.7.310 后指出：安装包里没有 `PenService.dll`，笔与键盘等配件逻辑在 `McuDevCo.dll`，其中 `IsPenConnectEventInfoComplete` 在缺少电量或充电状态时分别发送空载荷的 `0x08`、`0x09` 查询，没有定时查询。本机无法核对安装包内容；我们能核对的只是笔在主机侧的行为与该前提不符。

### 1.2 “MCU 不会自己报电量”

在主机侧没有观察到查询的条件下（见第 3 节条件），充电期间收到 7 次 `0x08`，值从 94% 到 100%，相邻间隔 38.2–44.7 秒。因此“必须查询才更新”在本机不成立。

严格性说明：我们没有对 `/vendor/bin/gk3pend` 反汇编，也没有做 USB 抓包。本机运行的这个文件 md5 为 `edf32e64f2d9da1e7eb6643f42d6b26a`（67,920 B）；我们从未替换过该系统文件，但也没有与 vendor 分区原始文件做逐字节比对，因此不能断言它与 ROM 打包版本一致。对应 dev 源码在打开设备时只发 `0x7101`、`0x7701` 两条常量查询，全文没有 `0x0801` / `0x0901`；`strings` 中也不含这两个字符串。以上只能支持“未观察到主机查询”，不能证明主机绝对没有发过。这一条按推断处理。

## 2. 被污染的数据（我们自己的问题）

同日 18:23 的一次抓取里，本机同时存在两个 `gk3pend`：系统原版与我们的补丁版。日志里 `claim/submit failed: 16` 累计出现 228 次。我们把原因归为两者争用同一个 `12d1:10b8` 的厂商接口，但没有抓包或驱动的直接证据；其它进程是否参与，也未验证。

那批数据中“电量约每 20 秒刷新一次”的结论不可用，已整批作废。原因是我们自己的补丁版与原版守护进程没有完全隔离，而不是笔的行为。此后所有记录都先证明“只有一个进程持有该接口”，再取数据。

## 3. 条件

- 抓取者：ROM 自带 `/vendor/bin/gk3pend -v`，未修改；同一进程连续运行、中途不重启（不重开 MCU，避免重握手干扰）。
- 独占：起跑前、运行中、各段之间都检查过，只有它持有 `/dev/bus/usb/003/002`；我们的补丁版与 watchdog 全部停止，系统服务 `vendor.gk3pend` 为 `stopped`。
- 笔与机身的链路（机主说明，本记录未独立验证）：机身侧面与笔端各有一枚无线充电线圈，充电走无线；笔与机身内那枚常驻 USB 设备 `12d1:10b8` 之间为私有近场 BLE。
- 实测：笔不在机身时，`3-3` 与 `1.0`/`1.1`/`1.2` 三个接口、`hidraw0`/`hidraw1` 全都存在，事件流静默。因此 USB 枚举不能用于判断笔是否在位。
- 时间基准：`gk3pend` 打印的是 CLOCK_MONOTONIC（不含挂起），`/proc/uptime` 是 BOOTTIME（含挂起）；本记录中某段熄屏后两者相差 640.78 秒，换算墙钟时已加偏移。

## 5. 结论与判据建议

- “满电”可以判断：`capacity=100` / 内核 `Full`，它就是笔报的电量；吸附瞬间即可成立，不代表“刚充满”。
- “停充那一刻”没有专属信号：只有 `0x09` 由 1 变 0，与真取下同值；4 次取下样本中 3 次同序、1 次相反（J）。顺序（G）与 `0x7b`（I）都有反例，不能当判据；USB 枚举与节点数值也不能。
- 因此主机侧无法在 `0x09=0` 到达时区分“满电停充”与“满电取下”。可落地的写法是按 `capacity` 分开表述：`100` 说“已充满”，`<99` 说“已取下”；代价是满电取下会被说成“已充满”。
- 能确认笔在机身上的停充只有两个样本（800 s、806.3 s）；另有一组 18.6 秒后掉充的样本归因不明（L），未计入。且两次的 100% 都在吸附前已达成，真实充满时刻未知；不能据此推出“充满后多久停充”。

## 6. 复现

```sh
getprop init.svc.vendor.gk3pend     # 期望 stopped，且确认没有第二个进程持有 12d1:10b8 的厂商接口
/vendor/bin/gk3pend -v              # 每条事件以开机毫秒开头
# 另一个 shell 采样节点
while :; do printf '%s up=%s cap=%s st=%s\n' "$(date '+%H:%M:%S')" \
  "$(cut -d' ' -f1 /proc/uptime)" \
  "$(cat /sys/class/power_supply/m-pencil/capacity)" \
  "$(cat /sys/class/power_supply/m-pencil/status)"; sleep 1; done
```

`-v` 的毫秒只增不减，但不含挂起时间；换算墙钟时须加上 `/proc/uptime` 与它的差值。
