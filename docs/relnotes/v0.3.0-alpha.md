## The machine can sleep now

Close the lid, walk away, come back. This is the first build where that works.

Every previous release said suspend was a kernel or EC defect, because it
reproduced identically under Linux on the same kernel. **That was wrong, and the
mistake was ours.** In Stage 2 this port changed one line of the device tree —
`usb_0`'s `dr_mode` from `host` to `otg` — to get USB device-mode adb. This
machine's UCSI is broken, so nothing ever tells that controller which role to
take; it settles into `device` with no gadget and no xHCI attached. Cutting power
to a controller in that state resets the whole SoC, with no panic, no oops and
nothing in pstore — which is exactly why it looked like a hardware-level defect
for four months.

Two things had to be true at once, which is why every single-variable experiment
came back negative and every hypothesis looked "eliminated":

1. the EC times out in `suspend_noirq` — fixed upstream, already in our kernel;
2. that USB controller must not be in `device` mode when the system suspends.

The fix keeps both halves of the trade-off: the port switches the controller to
`host` when the screen turns off and back to `device` when it turns on, gated by
a wakelock that is only released once host mode is **confirmed** — so any failure
means "no suspend", never "suspend into a reset".

⚠️ **The cost: while the screen is off, USB adb disconnects.** It comes back when
the screen turns on. adb over TCP (port 5555, on by default) is unaffected. If
you would rather not have this, `setprop persist.gaokun3.allow_suspend 0`
restores the old always-awake behaviour.

## Audio: headphone jack, and the microphones

**The headphone jack works.** So does the **built-in microphone** — which turns
out to have been completely dead until now, and nobody had noticed, because
nothing in the ROM recorded audio. The headset microphone works too.

The headphone jack was silent for an unusual reason: the audio routing was
incomplete inside the codec, in a way the kernel logs nothing about. The
interpolator stage of the RX macro was left at its reset defaults, so the DAPM
graph never completed, so the backend DAI could not be opened, so PCM open
failed — and no driver on that path prints a word about it. Nine mixer controls
later, playback runs at a measured 48,960 frames/second, which is real-time
48 kHz rather than a DMA engine spinning on nothing.

The recipe came from upstream ALSA UCM2, which turns out to treat this machine
as a ThinkPad X13s — `sc8280xp.conf` matches `HUAWEI.*MateBook E.*` and includes
the X13s profile verbatim. Speaker volume, headphone gain and mic gain are all
derived from the kernel's own dB tables rather than guessed.

## Hardware video decode: half of it

The kernel side of Venus is up — `/dev/video0` and `/dev/video1` are the
Qualcomm decoder and encoder, all clocks, power domains and IOMMU streams
resolve, and firmware loads. As far as we can tell this is the first SC8280XP
device with Venus running on mainline.

**This does not speed anything up yet.** Android still uses software decoders,
because it needs a Codec2 component that talks V4L2, and that is not wired up.
All 66 decoders remain software ones. Listed here because the hard, undocumented
half is done and the remaining half is ordinary work.

## Smaller things

* A watchdog now collects evidence when audio or Bluetooth deadlocks. It only
  reads `/proc` thread state — no `dumpsys`, nothing expensive — and fires only
  when the same thread has been in uninterruptible sleep for two minutes. Reports
  land in `/data/vendor/gaokun3/hangdump-<uptime>/`.
* Wi-Fi throughput to the internet is slower than it should be (roughly 1/20 of
  a laptop on the same network). Earlier notes blamed an ath11k defect; that was
  a misattribution — ping to the gateway is clean, LAN transfers hit 61 MB/s, and
  the driver logs nothing. The cause is still unknown.
* Recovery is built and shipped but **does not boot** — the entry is deliberately
  not created. `adb sideload` is not available; updates come through Settings and
  the rescue Linux can write any partition directly.

## Still missing

Camera. USB-C DisplayPort. Hardware video decode in Android. Ambient light
sensor, so no auto-brightness — that one lives on the SLPI DSP and its I²C
instance does not respond. SELinux is `permissive`.

The full, measured status table is in the
[README](https://github.com/vahiru/gaokun-android#status).

## Help wanted

Concrete, well-scoped work, roughly easiest first: a Codec2 V4L2 component so the
Venus hardware actually gets used (`external/v4l2_codec2` is already in the
manifest); the GPU SMMU interrupt mismatch in the device tree; a real thermal HAL
(⚠️ raise the SHUTDOWN thresholds at the same time — the AOSP mock reports 36 °C
and `ThermalManagerService` will power the machine off when it believes that);
SELinux enforcing; and the Wi-Fi throughput mystery above.

**Reports of what breaks are as useful as patches.** Open an issue with your BIOS
version and SKU, or come to the Telegram / QQ group.

The engineering record — every finding with its evidence, **including the
conclusions that later turned out to be wrong**, such as four months of blaming
the kernel for a suspend bug we introduced ourselves — is in
[`docs/`](https://github.com/vahiru/gaokun-android/tree/main/docs).
