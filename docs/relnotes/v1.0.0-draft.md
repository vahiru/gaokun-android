Android 16 (crDroid) for the **Huawei MateBook E Go** (Snapdragon 8cx Gen 3 /
SC8280XP) on a **mainline Linux kernel**, with hardware Vulkan on the Adreno 690.

The first release we call 1.0. It is mostly about being safe to hand to other
people: **release builds no longer open adb to the network**, the machine has
**its own boot entry that rolls back a failed update by itself**, and there is
a **fastboot mode**. The kernel moves from a release candidate to the **7.2.9
stable** kernel.

## Security advisory: network adb on v0.7.1 and earlier

**v0.7.1-alpha and every earlier release let anyone on the same network take
over the machine.** Those images listened for adb on TCP port 5555 on every
network interface — your hotspot included — accepted connections **without**
the "Allow USB debugging?" prompt, were debuggable (so `adb root` gave a root
shell), and carried the maintainer's adb public key.

From this release on, release builds:

* do not listen on port 5555, and adb is **off** until you turn it on in
  Developer options;
* ask you to authorize every computer (`ro.adb.secure=1`);
* are not debuggable (`ro.debuggable=0`), so `adb root` no longer exists;
* carry no maintainer key.

This takes effect with the update, nothing to do: the old port-5555 setting was
a built-in default of the image, and Android does not save those defaults to
`/data`. **The exception is anyone who ran `setprop persist.adb.tcp.port …`
themselves** — that value is stored on `/data` and survives the update. How to
clear it will be added to the known-limitations page (⬜ not yet verified on
hardware).

Two things to know if you use adb:

* After the update, adb over the network stops working until you set up
  *Wireless debugging* (pairing code) or authorize a computer over USB.
* **An authorized computer still gets a root shell**: root (KernelSU /
  ReSukiSU) is built in, and `adb shell` runs as root through it even though the
  build is not debuggable. Only authorize computers you trust.
* *USB debugging* switches itself back off at every reboot (⬜ not yet confirmed
  on hardware).

## The boot entry, automatic rollback and fastboot

**Android now has its own boot loader, gk3boot**, started by systemd-boot as the
default entry `Android`. It reads Android's A/B state in `misc`, picks the slot
and starts that slot's kernel straight from its boot partition — the job a
phone's bootloader does. It takes over after the first boot on 1.0 has finished
(that first boot still goes through the old per-slot entry). This release turns
it on by default.

* **A broken update rolls back on its own.** A freshly updated slot gets six
  tries; if it never finishes booting, gk3boot goes back to the previous slot and
  Android shows "rolled back to the previous version". Tested on the machine with
  a deliberately broken update that panicked six times in a row. A hang that never
  restarts still needs the power button.
* **A broken loader cannot lock you out.** If the `Android` entry fails to start
  three times, systemd-boot falls back to the old per-slot entry. Tested on the
  machine.
* **fastboot.** `adb reboot bootloader`, `adb reboot fastboot`, or the boot menu
  entry `Android fastboot / boot menu` start a small fastboot environment (cable
  in the USB-C port next to the power button). Checked on the machine:
  `fastboot devices`, `fastboot getvar all`, `fastboot oem device-info`,
  `fastboot reboot`, `fastboot reboot bootloader`, the volume keys in its menu,
  and that `adb reboot bootloader / fastboot / recovery` all land there and a
  pending request is cleared afterwards.

Not tested on the machine yet:

* `fastboot flash` (implemented, passes the emulator tests) — reinstall with the
  graphical installer instead for now.
* Confirming a menu item with the power button in fastboot mode.
* **Factory reset through this path** (see Known issues).
* Dual boot: making Windows the default system, and *Restart to Windows* from the
  new *Boot options* page in Settings.
* The first switch-over on a machine updating from 0.7.x.

To turn it off: as root, `setprop persist.vendor.gaokun3.gk3boot off` and reboot
once; the machine then boots exactly as before 1.0.

## Wi-Fi

* **Stable MAC address.** The Wi-Fi chip used to come up with a new MAC address
  on every boot, so routers saw a "new device" each time. The address is now
  derived from the SoC's serial number and stays the same across reboots (a
  locally administered address). It will differ once from whatever address you
  had before the update — if your router reserves an IP for the old one, update
  that reservation. Per-network random MAC addresses stay **off** in 1.0, as
  before: every network sees the same device address. (Not tested on hardware
  yet.)
* **Hotspot and Wi-Fi at the same time** should now work — the driver always
  supported it, the software configuration did not. (Not tested on hardware yet.)
* **5 GHz and WPA3 for the hotspot** are offered. (Not tested on hardware yet.)
* Network-connectivity checks have fallback endpoints that are reachable in
  mainland China. (Not tested on hardware yet.)
* Time sync tries `ntp.aliyun.com` first and keeps retrying; tested on the
  machine.

## Battery and standby

* **Standby switch in Settings.** *Settings → Battery → Standby (sleep)* turns
  standby off or on ("Allow standby") without a root shell. (Not tested on
  hardware yet.)
* **Charge limit (experimental).** *Settings → Battery → Charging control* can
  hold the battery at 70–80 %, through Huawei's embedded controller. (Not tested
  on hardware yet; we have not checked how the controller behaves at the limit.)
* **Wi-Fi stays connected in standby** (PR #40). Before, every standby
  disconnected Wi-Fi and powered the chip down, and it reconnected on wake.
  Data from the network still cannot wake the machine, so messages arrive at
  the next timed wake-up (see Known issues). If the connection drops during
  standby, it now comes back with the screen off; when the firmware
  occasionally declines to enter its standby mode, that standby is retried a
  second or two later instead of disconnecting (PR #46). (Not tested on a
  release build yet.)
* **Wi-Fi firmware crashes are recovered from**, also during standby; before,
  they could crash the kernel or leave Wi-Fi dead until the next cold boot
  (PR #44). (Not tested on a release build yet.)
* **The audio DSP can sleep in standby**, and memory clocks down in standby
  (five patches from mainline 7.3, PR #46). (Not tested on a release build
  yet.)
* **Battery usage per app** gets a power profile for this machine, so Settings
  can estimate which apps used the battery. The component currents in it are
  estimates. (Not tested on hardware yet.)
* **Sensors stop when the screen is off** and no app needs them; the sensor DSP
  used to stay awake all the time. Tested on the machine.
* Background apps are kept on the four smaller cores (Cortex-A78C, cpu0–3); the app
  in front can still use all eight. (Not tested on hardware yet.)
* The battery status from the embedded controller is decoded in more detail
  (adds a capacity level). Tested that the new values appear; not yet tested
  whether this fixes "charging while draining on a weak charger".

## USB and storage

* When a USB-C port gets into a bad state, or the tablet ends up powering the
  computer instead of the other way round, Settings shows a notification
  telling you to replug or reboot. (Not reproduced on hardware yet.)
* A mouse or USB stick plugged into the port next to the power button should
  stay connected when the screen turns off. (Not tested on hardware yet.)
* `/data` now keeps a small reserve (128 MiB) for the system, so a full disk
  cannot stop Android from booting. Tested on the machine.
* The port **next to the power button is back to USB 3** speed, and a power
  rail it needs is kept on, which fixes the board resetting when it went into
  standby as a USB device. Its role (host or device) follows what is plugged
  in, handled by a USB port service; plugging or unplugging in standby wakes
  the machine; several fixes in the USB-C controller driver (UCSI). Tested by
  the contributor; not on a release build with peripherals yet.

## Games

* ***Wild Rift* no longer closes right after launch** (it reaches the
  user-agreement screen; a match has not been tested): the kernel now hands
  out memory addresses below 2^39 by default, which the game assumes.
* **Apps are told a disguised kernel version**, `6.6.30-android15-8-…`, because
  some environment checks accept only 6.x or older; the kernel that runs is
  Linux 7.2.9. The rest of the system shows the real version, but crash records
  of apps carry the disguised one. *Settings → System → Kernel version spoofing*
  turns this off or changes the number. Do not use the KernelSU manager's
  *Install* / LKM patching: KernelSU is built into this kernel.
* Ordinary apps can no longer read the Wi-Fi card's hardware MAC address or the
  list of other devices on the local network; large OpenGL ES games keep more of
  their shader cache between runs.

## Known limitations

<!-- 一行一条，和 docs/known-limitations.md（main 2eac147）逐条对应；那边删了这边也删。 -->
The full list, with workarounds, is in
**[docs/known-limitations.md](https://github.com/vahiru/gaokun-android/blob/main/docs/known-limitations.md)**
([中文](https://github.com/vahiru/gaokun-android/blob/main/docs/known-limitations.zh-CN.md)). In short:

* **Security**: signed with Android's public test keys; `/data` is **not
  encrypted**; root (KernelSU / ReSukiSU) is built in, and any computer you
  authorize for adb gets a root shell; SELinux is `enforcing` (on a
  hand-partitioned disk the EFI partition may need renaming); the kernel
  reports a disguised version; the boot chain is unlocked. Network adb without authorization on v0.7.1 and earlier: see the
  advisory above.
  <!-- SELinux：D5（v1.0-plan §6）"批 2 三项验收都过就切，否则披露" —— 起草时所有 1.0 构建都是 permissive（V10 判据 getenforce = Permissive），⬜ 定稿前按 D5 的结果改。
       root 管理器是否预装（V7b）⬜ 未定：预装的话 known-limitations 那条第一句要改，这里跟着改。 -->
* **Proprietary components** ship in the images: Huawei firmware and sensor
  configuration, the Huawei Histen audio engine, and Google apps (MindTheGapps).
* **Not supported**: *Erase all data* in Settings (see Known issues; use the
  graphical installer's *Reinstall Android*); file transfer over USB (MTP); USB
  sticks; fingerprint (in progress); automatic brightness; GPS /
  location; DRM video (no Widevine); the microphone of Bluetooth headsets in
  calls, and of wired headsets; push notifications while in standby; Google
  certification (register once; Play Integrity never passes); no Chinese app
  store; no cellular network; no compass.
  <!-- U 盘（STOR-1）：V11 过了就从这里删。有线耳机麦（AV-10）：known-limitations 注释说"批 2 修"，起草时没有修复提交，照旧列。 -->
* **Other problems**: audio and Bluetooth can hang after a long uptime; plugged
  into a computer, the tablet may charge the computer instead; the USB-C port can
  stop working after replugging until a reboot; the stylus and palm rejection
  have drivers but are not yet checked on a release build; whether *Wild Rift*
  can play a match is not tested; on a weak charger the
  battery says *charging* while it drains. A Chinese input method (fcitx5) is
  preinstalled but has to be turned on once in Settings.

  hardware test passes (⬜ not yet tested).
