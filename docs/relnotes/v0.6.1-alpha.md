Android 16 (crDroid) for the **Huawei MateBook E Go** (Snapdragon 8cx Gen 3 /
SC8280XP) on a **mainline Linux kernel**, with hardware Vulkan on the Adreno 690.

This is a fix release for v0.6.0. **If the camera app crashed or showed nothing
on v0.6.0, this fixes it.** It also makes the rear camera usable in dim light,
wires up the flash LED in the kernel, and stops a wrong rear-camera module from
taking the front camera down with it.

## The v0.6.0 camera crash

On the v0.6.0 release image the camera app crashed on open, for everyone. The
software-ISP module libcamera needs was installed in `/vendor/lib64/` while
libcamera looks for it in `/vendor/lib64/libcamera/ipa/`. Without it libcamera
handed raw Bayer frames to the camera HAL, which treated them as RGB and read
past the end of the buffer. It had worked throughout development only because
the module had been placed by hand on the development unit. The install path is
fixed, and the HAL now refuses a non-RGB configuration and a short frame instead
of crashing ([#109](https://github.com/vahiru/gaokun-android/blob/main/docs/stage4-findings.md)).

## Rear camera

* **Exposure works in dim light.** libcamera now has a gain model and sensor
  properties for the OV13B10 (`gain = code / 128`, 1.12 µm pixels) and a tuning
  file, so auto-exposure can raise analogue gain instead of only stretching the
  exposure time.
* **A wrong rear module no longer kills the front camera.** Huawei shipped two
  rear modules for this board (OV13B10 and S5K3L6). Mainline camss waits for
  every sensor in the device tree before it creates any camera. This build makes
  it give up on a sensor that never binds after 20 s and continue with the ones
  that did — so on an S5K3L6 unit the front camera appears after a 20 s delay
  and only the rear is missing. If that is your unit, please tell us; the fix is
  a device-tree switch.
* **Flash and torch.** The flash LED sits on channels 1 and 4 of the PM8350C
  flash module — identified by lighting each channel in turn with someone
  watching the back of the tablet. The kernel exposes it as
  `/sys/class/leds/white:flash`, and the camera HAL now drives it: the
  flashlight tile in Quick Settings works, and the rear camera offers flash
  *auto* / *on* in the camera app. There is no strobe synchronised to the
  sensor, so "flash" here means the LED comes on at the app's pre-capture step,
  auto-exposure adapts to it over a few frames, and it stays on until the still
  frame has been captured. Torch-level current only (about 200 mA), so it is a
  fill light rather than a xenon-style burst.
* **Request settings were being ignored.** The HAL only read capture settings
  sent inline, but the framework sends them through the metadata queue first.
  Most requests therefore arrived with no settings at all; the camera worked
  only because the framework tolerates that. Fixed — which is also what makes
  the flash modes reachable.

## OTA on dual-boot installs

If your ESP's partition label is not exactly `esp` (typically a dual-boot
layout made by hand), v0.6.0's post-install step could not find the ESP and the
update failed on the last step. The post-install hook and the boot-control HAL
now locate the ESP by content (the vfat partition that holds our boot entries).

## Smaller things

* The updater manifest and downloads point at the R2 mirror again: GitHub
  release assets and raw.githubusercontent.com are not reachable from mainland
  China, and v0.6.0 users there could not update.
* The hang watchdog reads binder state from binderfs instead of debugfs (one
  SELinux blocker less). The camera HAL now runs in its own SELinux domain
  instead of `init`'s, and the media-controller device nodes are labelled.
  Still permissive overall.
* Kernel `#19`: patches `0035` (camss fallback) and `0036` (flash LED) on top of
  v0.6.0's `#18`; the never-lit GPIO93 "flash" LED is gone from the device tree.
* Two orphaned libcamera libraries from an old build (3.7 MB, referenced by
  nothing) are no longer in the image.
* Camera IDs are now stable: the rear camera is always camera `0` and the
  front `1`, as Android expects. Previously the order depended on which
  camera the kernel happened to register first, and could swap between
  boots.

## Known issues

* SELinux is still `permissive`.
* Audio (and Bluetooth) can deadlock after long uptime; a watchdog records the
  evidence under `/data/vendor/gaokun3/hangdump-*` — please attach it if you hit
  this.
* Colour is white-balanced but not calibrated (no colour matrix yet).
* Flash is torch-level fill light, not a synchronised strobe (see above).
