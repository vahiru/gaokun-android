# 《1.0.0 发版前修复计划》

> 依据：12 个方向的调研结果加复核结论（v0.7.1-alpha，构建戳 `1791053208`，2026-10-04）。严重度一律用复核者修正后的值。跨方向的重复条目已合并，合并后的严重度取所有被合并条目里最高的一个，原始 id 全部保留，便于回查。GitHub issues #11–#20 不在本计划范围内。

---

## 0. 现状判断

**离 1.0 还差的是"产品化"，不是"能跑"。** 主体功能实机可用：显示、触摸、GPU（turnip）、Wi-Fi、音频、iris 硬解、前后摄、加速度计和陀螺仪、待机挂起与唤醒、OTA 链路。7 小时开机里用户态系统组件没有发生原生崩溃，内存和温度也正常。缺口集中在下面四类：

1. **发布镜像用的还是开发机配置。** adb 不要授权就能用，5555 端口在所有网卡上监听，`ro.debuggable=1`，镜像里还有维护者自己的 adb 公钥。系统和 OTA 都用 AOSP 公开的 test-key 签名，`/data` 也没有加密。后两项在 1.0 之后再改，所有老用户都得迁移，所以 1.0 之前必须定下来。
2. **新用户的安装路径没在真机上走通过。** 整盘清空、双系统、默认的"清除数据重装"、从 U 盘启动、真实 Windows 上缩小 NTFS，这几条都只在 loop 设备或虚拟机里跑过。live 环境里按一下电源键或合上盖子，就可能在写盘中途断电。
3. **用户默认配置下的待机和长稳从没测过。** 开发机常年 `allow_suspend=0`，而且一直插着 USB。普通用户整夜待机掉多少电、几天不重启会不会出问题，目前没有数据。传感器 HAL 一直开着，SLPI 几乎不睡。
4. **用户能看到的文档和外部接口过时、偏开发者视角。** 两份 README 和 INSTALL、发版说明互相矛盾。安装指南只有英文。设备上看不到项目版本号。没有 FAQ，也没有固定的回归清单。

粗估：在用户能及时拍板的前提下，大约需要 **2 次内核构建、3–4 次 ROM 构建、1 次安装器重建、4–5 次用户在场的验收**。其中工作量最大、最不确定的是 B4（找一块真盘做安装验收）和 B2/B3（签名和加密，前提是用户决定要做）。

## 2. 阻断项（不修不能叫 1.0）

### B1 发布镜像默认开着免授权、能拿 root 的网络 adb，还带着维护者的公钥
**ids**：INST-1, OTA-1, PWR-1, APP-1, SEC-1, SEC-5, SEC-6, REL-1, BKUP-1（以及各方向 missed 里的 adbd 在 ksu 域、热点下同样暴露、公钥泄露主机名）
- **症状与影响面**：所有用户都受影响，一直存在。连上同一 Wi-Fi，或连上本机热点（#11 之后 hostapd 已进镜像）的任何人，执行 `adb connect <IP>:5555` 就能拿到 shell，不弹授权框，`ro.debuggable=1` 下再 `adb root` 就是 root。发布内核编进了 KernelSU（`CONFIG_KSU=y`），而且按 CLAUDE.md 的记录 ksu 域是 permissive，所以 enforcing 堵不上这个口子。指纹写的是 `userdebug/release-keys`，`ro.build.type` 却是 `user`，标识和实际不一致。
- **根因（已确认）**：Stage 2 为了让开发机不失联，在 `lineage_gaokun3.mk:64 WITH_ADB_INSECURE := true`、`:88-89 ro.debuggable=1`、`:143 PRODUCT_ADB_KEYS`，以及 `device.mk:42-43 persist.adb.tcp.port=5555`、`init.gaokun3.usb.rc:37-39` 里把这些都打开了，此后开发和发布一直共用这一份配置。
- **修复方案（按复核修正后的最简路径）**：保留 userdebug 变体，加一个开发开关（如 `GAOKUN3_DEV_BUILD`）。发布构建做四件事：①不设 `WITH_ADB_INSECURE`。按 `lineage_gaokun3.mk:51-57` 的注释，vendor/lineage 的 common.mk 会因此自动设 `ro.adb.secure=1` 和 `PRODUCT_NOT_DEBUGGABLE_IN_USERDEBUG`。②删掉 system_ext 里那行 `ro.debuggable=1`。③**显式清掉** `PRODUCT_ADB_KEYS`，因为 `refs/aosp-build/core/product_config.mk:488-495` 在 userdebug 下不会自动清除。④不再下发 `persist.adb.tcp.port`；`init.gaokun3.usb.rc` 开机时改成遵循 `persist.sys.usb.config`。init 的 permissive 能力由 Soong 的 Debuggable 决定（`init/Android.bp:126-134`、`soong_config.mk:58`），不受 ro.debuggable 影响，所以**这条不依赖 B1(enforcing)**，可以先发。`release.sh` 加断言。`sync-device-tree.sh` 对 adb_keys 的断言只在开发构建时生效。
- **第一步**：在 lineage_gaokun3.mk / device.mk 里加开关，编一版装到 `_b`，核对 5555 没有监听、USB 弹授权、`getprop ro.debuggable` 为 0。
- **还要验证**：ro.debuggable=0 下 KSU、自研 rc 和脚本是否正常；老用户 OTA 之后 `/data/property` 里有没有残留的 `persist.adb.tcp.port`，有就由首次开机或 postinstall 清掉；`INSTALL.md:311` 的 setprop 写法改成开发者选项里的"无线调试"配对；`install-ota-local.sh`、`find-device.sh` 等依赖 TCP 5555 的开发流程，改成在开发机上手动持久化。
- **工作量**：M。**需要**：ROM 构建、上机、用户决定（ro.debuggable 是否一起关）。

### B2 系统和 OTA 用 AOSP 公开 test-key 签名，R2 写密钥泄露后未见轮换
> **2026-10-04 用户定（D2）：保留 test-key、披露。** 本条不再阻断 1.0；剩下的工作是 ① 发版说明与 README 写明"用 AOSP 公开测试密钥签名，任何人都能签出本机接受的 OTA / 系统 App"；② R2 密钥轮换与域名续费照做（批 0）。下面的"换 key"方案留作以后参考。

**ids**：SEC-2（blocker），APP-2, REL-2, BKUP-3（major），SEC-7（R2 部分）
- **症状与影响面**：任何人都能用 AOSP 树里公开的私钥签出 update_engine 认可的 OTA 包，或者签出拿 system uid 的 APK。谁拿到了 R2 写权限或抢注了域名，就能给全部用户推送任意系统。在 1.0 之后再换密钥，所有老用户都要迁移，所以这是一道单向门。
- **证据**：实机 otacerts.zip 里只有 `testkey.x509.pem`，SHA256 `A4:0D:…:F5:DC`，与 `refs/aosp-build/target/product/security/testkey.x509.pem` 完全一致；framework-res 的证书 `C8:A2:…:2A:B8` 等于 platform.x509.pem；`release.sh` 里没有签名步骤；`TODO.md:69` 的 R2 轮换还是 ⬜。
- **根因（已确认）**：从没做过 `sign_target_files_apks`。
- **修复方案**：①**立刻做（不需要构建）**：在 Cloudflare 后台吊销 9-29 那把 R2 密钥，新令牌只授权这一个桶的写权限；域名开启自动续费；结果和日期记到 TODO:69。②生成私有密钥（离线备份），`release.sh` 改成 target-files → sign → `ota_from_target_files -k`。过渡版的 OTA 载荷仍用旧 testkey 签，载荷里带上新的 otacerts。平台签名迁移优先在构建机树里 grep Lineage 的 key-migration 机制，不要自己另写方案。
- **第一步**：在构建机上用一次性测试密钥签一份现有 target-files，装进 `_b`，看从 testkey 版保留数据升级时 PackageManager 的日志。
- **工作量**：L（R2 轮换为 S）。**需要**：用户决定、ROM 构建、上机。

### B3 `/data` 不加密：1.0 前必须定加不加（阻断的是这个决定，不一定是实现）
**ids**：INST-2, OTA-6, SEC-3, STOR-6, BATT-11（major）；APP-3, BKUP-2, BKUP-4（minor）
- **症状与影响面**：实机 `ro.crypto.state=unsupported`，`fstab.gaokun3:27` 没有 `fileencryption=`。开机菜单里常驻 gaokun3 installer 和救援系统，Secure Boot 是关的，拿到机器就能读出全部数据，锁屏密码不起作用。`docs/archive/stage7-installer-roadmap.md:86-88` 写着"Android 自己的 FBE 已经在管 /data"，这句是错的。以后要开 FBE 只能清数据：已有明文目录上设置加密策略会失败，init 会去请求 recovery（`builtins.cpp:426-436`），而本机没有 recovery，结果是无限重启。
- **限制条件**：KeyMint 和 gatekeeper 都是软件实现（`device.mk:68-78`）；主线内核没有 dm-default-key，所以元数据加密做不了。开 FBE 能带来的保护主要取决于锁屏密码的强度。开了以后，救援系统和安装器"保留数据重装"读不了 /data，开发排障也会受影响。
- **修复方案**：交给用户在两个选项里选：(a) **1.0 不加密**：改正 roadmap 那句话，在 README、INSTALL、发版说明里明确写"数据未加密，物理接触等于全部数据可读"（S）。(b) **加密**：fstab 加 `fileencryption=aes-256-xts:aes-256-cts:v2`（写法以构建机上的 fs_mgr/vold 源码为准），只对新装机和"清除数据重装"生效，绝不能通过 OTA 下发；先在测试盘上全新安装，验证开机、解锁、OTA 和 VAB 合并（L）。**建议选 (a)**，等有 TEE 方案或迁移工具后再上 FBE。
- **第一步**：不管选哪个，先改 roadmap:86 的错误说法。
- **需要**：用户决定；选 (b) 还需要 ROM 构建、安装器构建、上机和用户在场。

### B4 新用户的安装路径都没在真机上跑过
**ids**：GUI-1（blocker）、INST-7（major，接近 blocker）、INST-3（major）、GUI-6（minor，作为子项），以及 missed 里的"U 盘镜像从没在真机上从 U 盘启动过""默认的清除数据重装没验过""TODO B4 已过时"
- **症状与影响面**：新用户第一次安装就会走这些路，而这些路要么清空整盘、要么改动 Windows 分区，一旦失败代价无法挽回。真机上只验证过"从内置盘起 live 后重新安装并保留数据"这一种。
- **证据**：`INSTALL.md:44-48` 的能力表三项都是 ⬜；`:100` 写着 U 盘镜像没在硬件上启动过；`:9-10` 却说"每一版都是用这条路装的"，与前面矛盾；`stage7-flutter-debian.md:481` 列出了未验项；`INSTALL.md:24` 声称通用 Ubuntu ISO 可用，但没有任何依据。
- **根因（已确认）**：只有一台机器，而且是开发机，整盘都是 Android。
- **修复方案**：做 M4a。用外接 USB-NVMe 盘写入出厂布局（hw-inventory §8 的表加 NTFS 假数据），从 U 盘启动 live（同时验证插两个 USB-C 口各自的表现，即 GUI-6），依次跑整盘清空、双系统、默认的清除数据重装，每次都开机进 Android 并做一次 OTA。Windows 脚本找一位有 Windows 的群友完整跑一遍。在验证之前，`INSTALL.md:9-10` 和 `:24` 改成如实描述，命令行安装的首选环境改成我们自己的安装器 U 盘（切到 tty2 运行 `/usr/share/gaokun3/install-gaokun3.sh`）。
- **工作量**：XL。**需要**：上机、用户在场、用户决定（外接盘能否从固件启动 Android 需要验证，不行就得等用户同意重装开发机）。

### B5 live 安装器写盘期间，电源键或合盖可能关机、挂起，甚至整板复位
**ids**：GUI-2（blocker）
- **症状与影响面**：缩小 NTFS 或写 super 的过程中，用户习惯性按一下电源键、合上键盘盖，结果可能是 NTFS 损坏或盘写了一半。live 里 `a600000` 停在 role=device，没有 usbrole 守卫，按 #52 的结论，挂起会导致整板复位。
- **根因（疑似，基于 Debian logind 的默认行为）**：`scripts/live` 下没有任何 logind.conf.d、inhibit 或 sleep.target mask（`build-rootfs.sh:136` 只 mask 了 apt/e2scrub）。
- **修复方案**：在 overlay-common 加 `etc/systemd/logind.conf.d/gaokun3.conf`，把 HandlePowerKey、HandleSuspendKey、HandleLidSwitch*、HandleHibernateKey 都设为 ignore；`build-rootfs.sh` mask 掉 sleep、suspend、hibernate、hybrid-sleep 这几个 target，并在体检里加断言；`ShellBackend` 调用 gk3_apply、gk3_shrink、gk3_part_* 时套一层 `systemd-inhibit`。
- **第一步（只读）**：下次进 live 时，ssh 上去执行 `systemctl is-active systemd-logind` 和 `udevadm info /dev/input/event0 | grep power-switch`。
- **工作量**：S。**需要**：安装器构建、上机。

### B6 设置里的"清除所有数据"静默失效（隐私事故）
> **2026-10-04 用户定（D4）：做一个 fastboot。** 恢复出厂（BCB `--wipe_data`）、`adb reboot bootloader` / `fastboot`、`fastboot -w` 都落到它上面；下面的 (a)/(b) 作废，但"先清掉旧 BCB"的前置照旧。2026-10-05 用户澄清：要的是**统一的、承载启动 Android 的入口**（类 ABL）。设计见 [`boot-entry-design.md`](boot-entry-design.md)：推荐 **Y**（自研 `gk3boot.efi` 作所有 Android 启动的唯一入口：读 misc 选槽扣 tries 自动回落、分派 BCB、从 `boot_x` 分区直接启动；fastboot / 恢复出厂 / 引导菜单由同一内核 + 静态 initramfs 里的 `gk3-fastbootd` 执行），约 8–10 人周，硬门槛是 E4（缓冲区 LoadImage 真内核）；待用户定 U1–U11。旧稿 [`fastboot-design.md`](fastboot-design.md) 的 C′ 推荐作废、执行端沿用。

**ids**：OTA-4, INST-13, SEC-8, BKUP-8（均为 major），A5；missed 里的"misc 中残留旧 BCB 的隐患"
- **症状与影响面**：用户卖机或送修前点了"清除所有数据"，重启后数据都还在，用户却以为已经清掉。再叠加 B3 的不加密，这是真实的隐私泄露路径。
- **根因（已确认）**：BCB 加 recovery 的路径在本机没有执行者：systemd-boot 不读 BCB，recovery 启动后陷入复位循环（#39）。
- **修复方案（1.0 最低要求，二选一）**：(a) 用 overlay 把入口隐藏或替换成一页说明（资源名要在 Settings 源码里 grep 确认）；(b) 在 `init.gaokun3.rc` 的 `on fs`、`mount_all` 之前，用 vendor 小程序读取 misc：如果是 `boot-recovery --wipe_data`，就把 userdata 开头清零，交给 `formattable` 重新格式化，并同时清 metadata（否则 VAB 状态会出问题，参见 INST-13）；`--prompt_and_wipe_data` 只清 BCB。**无论选哪个，都必须先清除现存的旧 BCB**（在 postinstall 或安装器里把 misc 清零），否则老用户升级后第一次开机可能执行几个月前误点的清除。INSTALL 里的 mkfs 写法统一改成"图形安装器 → 重新安装 + 清除数据"。
- **工作量**：(a) S / (b) M。**需要**：ROM 构建、上机、用户在场（(b) 会真的擦数据）、用户决定。

### B7 用户默认配置下的待机和长稳缺少实测（验收型阻断）
**ids**：PWR-2, PWR-7, LIVE-3, PERF-3, PERF-4（均为 major，复核意见是合并成一项测量任务）；missed 里的"DDR 常驻 1017 MHz""SLPI 5 Hz 中断打在大核上""小核从不降到 691 MHz 以下"
- **症状**：README 写着待机 ✅，但验收只做过 3.5 分钟的 force-idle 和 8 次短挂起。这次开机里 3 次真 s2idle（插着线，各约 2.6 秒）之后，cxsd、aosd、ddr 计数全是 0。这只能算弱证据，说明不了真实待机深度。72 小时多日运行加反复挂起这种组合从没跑过（#16 在报告者那里是开机约 14 小时后才出现的）。
- **根因**：未知。开发机为了让 adb 一直在线，关掉了待机。
- **修复方案**：在用户在场、拔掉 USB 的条件下：①设 `allow_suspend=1` 放置 8 小时，前后各读一次 `qcom_stats/{aosd,cxsd,ddr,slpi,adsp}`、`charge_now`、`suspend_stats`，采样写在设备本地；②亮屏硬解播放 1 小时；③72 小时狗粮测试（PERF-12 C 档）。用 `persist.sys.boot.reason.history` 区分断电和正常重启，不要只看有没有 SHUTDOWN 记录（BATT missed）。如果 cxsd 仍是 0，按"修 PWR-3 → 查 ADSP → 查 ICC 投票（PCIe/USB）→ 去掉 pd_ignore_unused"的顺序逐个排查。
- **第一步**：写一个只读采样脚本（每次唤醒追加一行到 /data/local/tmp），在批 1 镜像上跑。
- **工作量**：L（测量部分为 M）。**需要**：上机、用户在场；修复阶段可能需要内核构建。

## 5. 分批执行路线

按"构建周期 + 一次上机验收"来分批，需要用户在场的步骤尽量集中到同一次。

### 批 0：不需要构建，现在就能做（1–3 天）
- **安全**：轮换 R2 密钥，域名开自动续费，查 R2 用量（B2 ①、REL-8）。
- **文档对账**：README 中英两版的硬矛盾（INST-8/REL-3/AV-17，包括手掌拒绝那句）、roadmap:86 的 FBE 错误说法（B3）、TODO 全表对账（REL-12）、7 个 issue 模板（REL-11）、INSTALL 里的 R2 链接、前置条件、相对链接、`:9-10`/`:24`/`:154` 这几处（INST-3/5/15/20、GUI-16）、CLAUDE.md:82（OTA-3）、删掉 `ota/gaokun3.json`（REL-14）、把 deploy 脚本挪去 archive（INST-19）。
- **披露**：发版说明加"不支持/已知问题"整节，包括 root、未加密（按 B3 的决定写）、专有组件、Widevine、BT 通话、U 盘、MTP、指纹、手写笔、定位、待机期间不收推送（SEC-10/12、REL-10/15、AV-2/9、DISP-13、HW-5、APP-12/13）。
- **工程**：建 `docs/release-checklist.md`（REL-6）；v0.7.1 的 GPL 源码清单先从实机 config.gz 补一份（REL-7）；性能和采样脚本先写出来（PERF-2、B7）。
- **要用户做的**：做出第 6 节里的各项决定；看一眼 USB-C 孔对应哪个 port（STOR-3）；收集各变体的 DMI 信息（INST-22）。

### 批 1：ROM 构建 #1，安全与稳定基线，不动内核、不格式化（约 1 周）
**内容**：B1 adb 和发布构建开关加 release.sh 断言；LIVE-1 lights HAL；PWR-3 传感器引用计数；PWR-5/STOR-2 usbrole 的 has_downstream；PWR-4 止损通知；STOR-1 voldmanaged；STOR-5 reservedsize；NET-1 软件 PNO；NET-12 NTP 顺序；APP-8 GLES；APP-9 超时倍数降到 2；HW-7 feature xml；HW-12 minDelay；LIVE-4 smmu 退避；AV-6 hangdump 判据；OTA-8/9 postinstall；**清除旧 BCB**（B6 的前置）；B6(a) 隐藏或替换恢复出厂入口（如果用户选 a）；OTA-11 和 REL-5 的版本属性与断言；REL-4 Updater 链接；SEC-14；REL-13 断言。
**为什么这样分**：都是配置和用户态改动，一次 ROM 构建就能覆盖，风险低，而且 B1 越早发越好。
**验收**：装到 `_b`，用 oneshot 启动。无人值守项：A 档清单、5555 不监听、`sm list-volumes`（bind-mount 预验证）、`qcom_stats/slpi` 计数开始增长、`smp2p-slpi` 降到 0/s。**用户在场（集中一次，约 1.5 小时）**：插 U 盘（两个孔，port0 上做亮屏、息屏）、USB 授权弹窗、合盖三种姿态的 getevent（DISP-1）、方向 A/B（DISP-2）、录屏和录像（AV-1）、开机菜单的无键盘操作（INST-18）、金融类 App 第一轮测试（APP-4）、前摄方向（AV-12）。

### 批 2：内核构建 + ROM 构建 #2，基线升级和驱动修复（约 1–2 周）
**内核**：SEC-9 升到 7.2.y stable（这是最大的回归风险，所以和其他内核改动一起做，只做一轮回归）；BATT-1/2/3 电池驱动（按位解码、capacity_level、温度）；NET-3 USB 网卡改 =y；NET-8 android-base 网络配置；LIVE-8/12、LOG_BUF_SHIFT、THERMAL_STATISTICS、APP-17；EC 初始 LID 状态；HW-9 隐私灯；DISP missed 的 DPI；（可选）DISP-5 HID fixup。
**ROM**：DISP-1 lid overlay（批 1 测过之后）、DISP-2（按决定）、DISP-3 中文输入法（按决定）、NET-2 STA+AP、NET-4 MAC、NET-7、NET-10、DISP-14/HW-1 SSC 恢复守护、AV-1 修复、AV-4、AV-10、AV-16、BKUP-5、HW-6、PERF-6 第一步、LIVE-5、PWR-14、PWR-16 和 Parts 开关、DISP-15、DISP-6、B6(b)（如果选这条）、SEC-4 第一阶段策略（如果决定切 enforcing）。
**验收**：先按 `kernel-apply-patches.sh --verify` 绿灯才编；跑 A 档清单，回归触摸、相机、iris、待机。**用户在场**：插电脑 USB 口带负载放电，采样 0x82（BATT-1）；热点加 Wi-Fi 同时开；DP 显示器（DISP-4）；USB 网卡；B6(b) 真擦一次数据（先备份）；`enforcing` 下拔线待机加回插（SEC-4）。

### 批 3：安装器构建 + 真盘验收（B4，耗时最长，可以和批 2 并行）
**内容**：B5 logind 和 inhibit；GUI-3/5 失败页和下载；GUI-20 默认 64 GiB；STOR-5 `mkfs -m 0`；GUI-7/INST-11 的 ps1 BitLocker 顺序；INST-6 救援镜像放进 Release；INST-17 增加 slot_b 救援条目；INST-12 的 gk3-boot-android；GUI-4/8/9/11/12/13/14/17/18/19、INST-10/16、BATT-8；OTA-2 启动计数（HAL 和 postinstall，属于 ROM 侧，但和"回落"的验收放在一起做）。
**验收（用户在场，最好安排一个整块的半天）**：外接盘写成出厂布局 → 从 U 盘启动（两个孔各一次）→ 整盘清空 → 开机并 OTA 一次 → 双系统 → 默认的清除数据重装 → 首次开机向导完整走一遍并截图（OTA-13）→ OTA-2 的演练：让新槽故意起不来，看能否自己回落。Windows 脚本找群友在真 Windows 上跑。

### 批 4：只在 1.0 前做一次的测量与长稳（B7、PERF-2）
**内容**：B7 拔线 8 小时待机、亮屏硬解 1 小时、72 小时狗粮测试；PERF-2 游戏基线（含 UBWC 的 A/B、60 还是 120 的确认）；APP-5 推送延迟；AV-3/8/13/14/15 音频、蓝牙、通话；LIVE-7 60/120 Hz 电流对比；PERF-5；以及其余标着"4"的验证项。根据结果决定是否追加内核修复（PWR-10、ICC 投票）。
**为什么放这里**：要等批 1 的传感器修复和批 2 的 stable 内核都进了镜像，量出来的数字才有代表性。

### 批 5：1.0 RC（签名按 D2 不换；FBE 按 D3 不做）
- 如果 B2 决定换 key：先发过渡版（testkey 签载荷，载荷里带新 otacerts），1.0 再用新 key 签名，在 `_b` 上演练两跳保留数据升级。
- 如果 B3 决定开 FBE：只在新装机上启用，用外接盘全新安装来验证。
- RC：用 1.0 的 boot.img 重新构建安装器（GUI-15）；跑完整的 A/B/C 三档清单；GPL 源码清单；中英文发版说明；`release.sh --no-build`。

**用户在场的步骤汇总**：批 0（决定和看孔位，约 30 分钟）→ 批 1 验收（约 1.5 小时）→ 批 2 验收（约 2 小时，含放电和擦数据）→ 批 3 真盘半天 → 批 4（放电过夜加 72 小时日常使用加约 1 小时游戏）→ 批 5 RC（约 1 小时）。按 memory 的约定，重启、装内核、擦数据、放音之前都要事先征得同意，并尽量合并成一次做完。
